# Godox iT30Pro 固件刷写技能

逆向 Godox 官方升级器（Godox V2.0.exe）所得的完整刷写能力，可替代官方工具且更可靠（逐块 ACK 验证、失败即停、支持任意自定义固件）。

## 适用设备

共用 `iT30ProSiT30SV480S` 固件镜像的机型：iT30Pro S/C/N/F/O、iT30S、V480 系列。
Gr 模式组结构：**M = 本机机顶闪（组 0）**，**A/B/C = 引闪组（组 1-3）**。

## 前置条件

1. USB-C 线连接电脑
2. 设备进入升级模式（两种方法）：
   - **关机状态按住 MENU 键不松，插入 USB**（最可靠，固件损坏也能进）
   - 开机 → 菜单 → 设备信息页 → 点"固件升级"
3. Python 3（脚本纯标准库 + ctypes，无第三方依赖）

## 设备识别

| 状态 | HID | 产品字符串 |
|---|---|---|
| 升级模式 | VID `0x0483` PID `0x572B` | `Godox_IAP` |
| 正常模式 | 同 VID/PID | 查询响应返回机型名（如 `iT30ProS`）|

枚举检查：`python scripts/hid_scan.py`

## 核心工具

`scripts/godox_iap.py`（依赖同目录 `hid_scan.py`）：

```bash
# 查询设备状态/身份（非破坏性）
python scripts/godox_iap.py --query

# 刷写固件（必须加确认标志）
python scripts/godox_iap.py --flash <固件.bin> --i-know-this-bricks

# 干跑（只构建包不发送，验证文件）
python scripts/godox_iap.py --flash <固件.bin> --i-know-this-bricks --dry-run
```

## 刷写协议速查（逆向自官方升级器）

### 请求报文（65 字节 HID 输出报表）

```
[0]=0x00 报表ID占位
[1]=0xAA [2]=0x55 [3]=CMD
[4..4+L)=payload
[4+L..61)=0xFF 填充
[61..65)=chk32 大端 = sum(bytes[1..61])
```

| CMD | 功能 | payload | 设备响应 status |
|---|---|---|---|
| 0x00 | 查询 | 无 | 0x01 |
| 0x02 | 擦除全镜像 | 无 | 0x03（约 2.1s，真实扇区擦除）|
| 0x08 | 写块头 | 8B = [块号 BE32][chk32 BE] | 0x05（收满 1024B 后）|
| 0x01 | 重启 | 1B（0x55）| 无 |
| 0xA0 | 查询设备信息 | 无 | 0xA1 + 32B 机型名 |

- 写块：每块 1024B = 1 头报表（CMD=0x08）+ 16×64B 数据报表（`[0]=00` + 64B 裸数据）
- 全镜像 688182 字节 = 673 块
- **每块必须等待 ACK，未收到立即中止**

### 响应报文（65 字节 HID 输入）

`[0]=00 [1]=AA [2]=55 [3]=status [4..]=body`

### 固件文件格式

```
[镜像 0xA8000B][MD5(镜像) 16B][名称 28B 如 iT30ProSiT30SV480S_V1.07.bin][u16=0x1C][魔数 AA55669977882233]
```

- 升级器只校验 MD5(镜像)==trailer MD5；trailer 名称决定升级器/设备的版本显示
- **官方升级器"更新设备成功"提示不可信**：发完数据即报成功，从不验证设备执行

## 安全规则（务必遵守）

1. **每块必须等到 ACK**（status 0x05），任何一块无响应立即中止
2. bootloader 独立于应用固件——刷坏后"关机按住 MENU 插 USB"可重新进入升级模式恢复
3. 擦除是真实扇区擦除（约 2.1s）；**擦后不写 = 应用区全 FF = 无法开机**，需重刷恢复
4. 官方升级器的"网络文件"按钮会下载原版覆盖自定义固件
5. 本机灯头（M 组）放电参数表原生覆盖 1/256-1/512，扩展档位输出安全
6. **验证刷写是否生效要看功能行为（如 1/256 档位），不要看版本号**——版本显示来自 IAP bootloader 区（刷写永不覆盖），永远不变

## 功率模型（1/256 扩展的核心知识）

- 每组功率 = `byte_2000058C[组]`（tenths：0=1/1 满功率、70=1/128、80=1/256、90=1/512）
- 档位显示是数学公式（分母 = 512 >> ((90-tenths)/10)），**不是图标资源**
- Gr 模式：组 0 = M（本机机顶闪），组 1-3 = A/B/C（引闪）
- 官方边界：tenths ≤ 0x46（70 = 1/128）——共 18 处 clamp：
  - M/Multi 控件渲染 0x800ABCC/0x800B8BC（0x800ABE4/ABEC、0x800B8D8/B8E0）
  - 主面板 0x800D048（0x800D158/D15E）
  - UI 副本 0x8008E60（0x8008FEC/FF0/004/026）
  - **配置校验器 0x800AA2C**（0x800AA4A 常量 + AA6E/AA94/AAA0）——保存/开机时强制拉回 70！
  - 无线命令 188/189（0x800F70C 内 0x800FBAC/FBB4/FBBE/FBCA）
- 无线协议**原生支持 1/256**（case 178 阶梯含 0x50）
- 本机灯头放电表按 `80 - tenths` 索引，原生覆盖至 1/512

限制分**三层**，任一层都足以把档位卡在 1/128，改补丁必须同时处理：

1. **取值钳位**：上面列出的 18 处 `>0x46 → 0x46`（校验器 / 配置加载 / 渲染）
2. **滑条范围与换算**：`sub_803D014` 的 `movs r2, #0x47`（滑条 max = 71）、
   `#0x15`（1/3 档上限 21）以及 `rsb #0x47` 反算
3. **步进函数**：`sub_8014E40` 尾部（`0x08014FB2`）对结果做 `0x46` / HSS 时 `0x28`
   的统一上限——波轮、触屏 `+`/`-`、ALL 全组调节全部经过这里

`patch_gr256.py` 的做法是**按组区分**：读取实时组号与 `byte_200003D8`（Gr = 3），
Gr 的 A/B/C 允许 `0x50`（1/256），M 组与非 Gr 模式保持 `0x46`（HSS 下 `0x28`）。

## 固件变体

| 变体 | 内容 |
|---|---|
| 原版 V1.07 | 官方版本，全组功率 1/128–1/1 |
| `patch_256_v2.py` | 历史：tenths 0x46→0x50、thirds 0x15→0x18、滑条 max 0x47→0x51 |
| `patch_256_v3.py` | 历史：v2 + 18 处 tenths clamp（触屏可达 1/256，波轮仍停在 1/128）|
| **`patch_gr256.py`** | **当前推荐**：按组区分——Gr 的 A/B/C 在触屏滑条、触屏 `+`/`-`、波轮、ALL 全组调节下均可到 1/256；M 组保持 1/128（HSS 下 1/16）|

补丁生成器位于仓库根 `patches/`，实现细节见 `docs/power-model.md`
（code cave @ `0x0808FA80`，22 处 BL/B.W 重定向）。

## 已知遗留问题

- 波轮路径已由 `patch_gr256.py` 修复：限制点其实在共享步进函数 `sub_8014E40`
  的尾部（`0x08014FB2`）以及各调用点的写入钳位，此前"运行时数据驱动"的判断不成立
- `0x0801EB28` 的 `movs r0, #0x46`：调用者不明，未改动；若发现某处仍被拉回
  1/128，优先检查它
- Multi（频闪）功率仍为官方 1/128–1/4，本次未扩展

## 故障排查

| 症状 | 原因/处理 |
|---|---|
| 刷写中 "NO ACK" | 设备状态异常——重新进升级模式再试 |
| 触屏死机重启 | 补丁的 IT 指令编码错误（mask bit3 必须=1：ITE=0x0C 而非 0x04）——检查新增指令编码 |
| 版本号不变 | 正常！版本来自 IAP bootloader 区，刷写永不覆盖——用功能行为验证 |
| 查询无响应 | 设备在正常模式而非升级模式，或升级软件占用了 HID（关闭 Godox 升级软件）|
| 擦除无响应 | 擦除需约 2.1s，等待至少 25s |
| 触屏调 1/256 后被拉回 1/128 | 配置校验器 0x800AA2C 在保存/开机时 clamp——需按组改造校验器 |
